# API modules

`auth`, `users`, and `audit` hold the Phase 2 foundation: JWT access and refresh tokens (`jose`, HS256), opaque refresh sessions in PostgreSQL, email/password registration and login, a development bearer-token seam, server-side permissions, and append-only audit writes. JWT payloads do not include roles; `authenticate` loads grants from the database.

`catalogue` is the Phase 3 discovery and host-onboarding module: cities, languages, categories, host verification, experience listings, availability, and admin review. Public slot responses include `remaining` seats after active holds. Identity documents are private storage references only. Object storage is not configured, so uploads and document bytes are unavailable. Role assignment has no public route.

`bookings` is the Phase 4 request, offer, and booking module. A traveller trip request and a slot booking are idempotent when the same `Idempotency-Key` and body are retried. Accepting an offer or creating a slot booking snapshots price, commission (or zero when no policy row is effective), and cancellation terms, then leaves the booking in `AWAITING_PAYMENT` with `payment.state` of `NOT_STARTED`. Listing base price and offer price are booking totals; party size only reserves seats. Slot holds last 15 minutes and are released by cancellation, expiry, or a later reservation that finds them lapsed. There is no API transition into `CONFIRMED` and no payment attempt is created. PostgreSQL row locks and `enforce_slot_capacity` keep the last seat from being sold twice. One pending offer per host and request is a partial unique index in SQL.
